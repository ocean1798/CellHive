# Air780EPV 智能随身通信网关架构与实现规范

## 1. 架构定位与设计哲学

基于对移芯 EC718P-V 芯片底层内存与物理分区的实测事实（官方固件 LittleFS 用户空间固定为 **128KB**，Lua 可用堆内存固定为 **128KB**），系统推翻“魔改底层 C 分区”与“板端硬跑重度 Web”的过度设计方案，确立**“板端坚决做轻、防御性配置优先、按需激发能力、上位机承接交互”**的务实架构：

- **防御性配置（安全保号）**：随身上网（RNDIS 网卡）**默认彻底关闭**，杜绝 Windows 后台更新偷跑流量；
- **信令通信优先**：短信收取与来电拦截走纯信令通道，不依赖 4G 数据流量，卡内 0 流量亦可安全运行；
- **按需激活高阶外设**：需要电脑 4G 上网时，通过上位机一键动态点亮 RNDIS 网卡；
- **分工明确**：板端专注 4G 射频与脱机黑匣子（100 条防丢缓冲），复杂的界面渲染、海量历史归档（SQLite）与 AI Agent 对接全部交给宿主机（PC/NAS）。

## 3. 板端严密资源账本（确保永不爆仓）

在将 P0 ~ P3 全部加载到模组后的资源占用审计：

1. **Flash LittleFS 用户文件系统（总额 128 KB）**：
   - 基础配置文件（`fskv`）：~2 KB
   - 短信黑匣子（100 条短信环形队列）：~25 KB
   - 随身上网开关标志位：~0.5 KB
   - **合计常驻仅占用约 28 KB，剩余 100 KB（空闲率高达 78%）**！
2. **Lua 堆运行内存（总额 128 KB）**：
   - 业务状态机 + 短信与电话解析：~15 KB
   - 串口收发缓冲区 + 网络 HTTP 请求：~15 KB
   - **合计常驻仅占用约 30 KB，剩余 98 KB（空闲率高达 76%）**！彻底消除 OOM 隐患。
3. **宿主算力与海量存储（P4）**：
   - 运行在 PC / NAS 端，消耗电脑的 CPU、GB 级内存与硬盘，对单片机零负担。

## 4. 核心功能实现设计

### 4.1 通信感知与 0 话费来电拒接（P0）
- **短信捕获**：
  监听 `SMS_INC` 事件，提取发件人号码与正文，通过正则表达式：
  `local code = content:match("(%d%d%d%d%d?%d?)")`
  快速抽取出 4~6 位验证码，优先打包送入串口和飞书。
- **来电拒接**：
  监听 `CC_IND` 事件。一旦收到 `INCOMINGCALL` 振铃状态，立即执行两步原子操作：
  1. `local from = cc.lastNum()` 毫秒级提取号码并向飞书/串口发布事件；
  2. 立即执行 `cc.hangUp()` 主动拒接，**全程双方 0 话费，无任何音频处理开销**。

### 4.2 板载断网黑匣子持久化（P1）
- **存储文件**：`/sms_box.jsonl`（每行一条 NDJSON 记录，便于追加与切片）。
- **环形淘汰与 GC 协同算法**：
  - 内部计数器达到 100 条上限时，采用批次淘汰（批量淘汰前 20 条，重写剩余 80 条），减少 Flash 擦写频次；
  - 重写文件后，**必须显式调用 `collectgarbage("collect")`**，立即释放字符串重组产生的临时堆内存，将 Lua 堆稳定压制在 53KB；
  - 写入操作由底层 LittleFS 执行全局磨损均衡，单片机 NOR Flash 擦写寿命超 10 年。
- **流式防爆内存读取**：
  - 上位机请求拉取历史时，板端使用 `io.open` 逐行读取并输出，每次仅占用几百字节缓冲区，严禁一次性全量装入 Lua Table。

### 4.3 随身上网动态受控切换（P3）
- **启停控制与热复位时序**：
  在 EC718PV 芯片中，修改 USB 复合设备模式（CDC ACM + RNDIS）需要重新向 USB Host 声明设备描述符。采用“两阶段握手时序”：
  1. **第一阶段（即刻回执）**：板端收到 `{"cmd":"set_rndis","params":{"enable":true/false}}` 后，先向 `VUART_0` 用户虚拟串口返回响应帧 `{"type":"res","msg":"RNDIS_SWITCHING", ...}`，确保上位机收到确定性 ACK；
  2. **第二阶段（延时热复位）**：延时 500ms，板端执行 `mobile.config(mobile.CONF_USB_ETHERNET, enable and 1 or 0)` 并调用 `rtos.reboot()` 软重启；
  3. **上位机自愈重连**：PC 上位机后台线程捕获 USB 重新枚举引起的瞬断，并在设备重新就绪后无缝重连恢复通信。
- **安全保障**：开机初始化脚本中默认执行 `CONF_USB_ETHERNET = 0`，只有收到上位机明确命令时才临时开启。

### 4.4 串口通信协议（上位机直连接口）
板端与上位机通过 **USB 虚拟串口（VUART_0 用户口，Windows 下由动态探测定位如 `COM8`/`COM16`，Linux 下为 `/dev/ttyACM1`，`uart.VUART_0` ID: 32）**交互，采用行分隔 JSON（NDJSON，以 `\r\n` 结尾）：
- **分包粘包防护**：板端内置行累加器（`line_buffer`），只有收到完整换行符后才送入 `json.decode`，有效规避 USB CDC 块传输分包/粘包异常。
- **上位机串口参数**：波特率 115200、8N1，**打开端口后必须设置 `DTR=True` 与 `RTS=True`**，否则 CDC-ACM 不下发数据。

- **板端主动事件广播（模组 ➔ 上位机，`type: "event"`）**：
  - 网关就绪：`{"type":"event","event":"gateway_ready","data":{"bsp":"Air780EPV","csq":27,"temp":"37.00","vbat":"4.00","rndis":false}}\r\n`
  - 收到短信：`{"type":"event","event":"sms_rx","data":{"from":"+8613800138000","content":"...","code":"892104","time":1789008801}}\r\n`
  - 来电拦截：`{"type":"event","event":"call_rx","data":{"from":"+86138...","action":"REJECTED_ZERO_COST","time":1789008801}}\r\n`
  - 短信投递报告：`{"type":"event","event":"sms_tx_report","data":{"id":"cli_123","success":true}}\r\n`
  - 周期心跳：`{"type":"event","event":"status","data":{"csq":27,"rsrp":-89,"temp":"37.00","vbat":"4.00","rndis":false,"lua_mem_kb":53}}\r\n`

- **上位机下发指令与应答（上位机 ➔ 模组，`type: "cmd"` ➔ `type: "res"`）**：
  - 状态查询：
    - TX: `{"type":"cmd","id":"1","cmd":"get_status"}\r\n`
    - RX: `{"type":"res","id":"1","code":0,"msg":"STATUS_OK","data":{"bsp":"Air780EPV","csq":27,"rsrp":-89,"temp":"37.00","vbat":"4.00","blackbox_count":1,"rndis":false,"lua_mem_kb":53}}\r\n`
  - 发送短信：
    - TX: `{"type":"cmd","id":"2","cmd":"send_sms","params":{"phone":"13800138000","text":"验证码测试"}}\r\n`
    - RX: `{"type":"res","id":"2","code":0,"msg":"QUEUED_TO_BASE_STATION"}\r\n`
  - 查询黑匣子历史：
    - TX: `{"type":"cmd","id":"3","cmd":"get_history","params":{"limit":10}}\r\n`
    - RX: `{"type":"res","id":"3","code":0,"msg":"HISTORY_OK","data":{"count":1,"total":1,"items":[{"sender":"+86132...","content":"...","otp":"778899","time":1789008801}]}}\r\n`
  - 清空黑匣子历史：
    - TX: `{"type":"cmd","id":"4","cmd":"clear_history"}\r\n`
    - RX: `{"type":"res","id":"4","code":0,"msg":"HISTORY_CLEARED","data":{"total":0}}\r\n`
  - 控制随身上网：
    - TX: `{"type":"cmd","id":"5","cmd":"set_rndis","params":{"enable":true}}\r\n`
    - RX: `{"type":"res","id":"5","code":0,"msg":"RNDIS_SWITCHING","data":{"enable":true,"reboot_required":true}}\r\n`
  - 查询运行时间与自动重启状态 (P5)：
    - TX: `{"type":"cmd","id":"6","cmd":"get_uptime"}\r\n`
    - RX: `{"type":"res","id":"6","code":0,"msg":"UPTIME_OK","data":{"uptime_seconds":15,"reboot_hours":0,"next_reboot_seconds":-1}}\r\n`
  - 动态配置周期自动重启 (P5)：
    - TX: `{"type":"cmd","id":"7","cmd":"set_reboot_policy","params":{"hours":24}}\r\n`
    - RX: `{"type":"res","id":"7","code":0,"msg":"REBOOT_POLICY_UPDATED","data":{"reboot_hours":24,"next_reboot_seconds":86400}}\r\n`
  - 立即重启设备 (P5)：
    - TX: `{"type":"cmd","id":"8","cmd":"reboot","params":{"reason":"cli_reboot"}}\r\n`
    - RX: `{"type":"res","id":"8","code":0,"msg":"REBOOT_COMMENCED"}\r\n`

## 5. 典型运行拓扑

1. **PC 随身工作拓扑**：
   - 板子插在笔记本 USB 口，上位机常驻后台（右下角托盘）；
   - 平时：0 流量接收验证码和来电弹窗；
   - 紧急时：点击右下角“开启 4G 网卡”，笔记本直接获得网络。
2. **家庭 NAS 24 小时通信拓扑**：
   - 板子插在 NAS USB 口，NAS 启动 Python/Docker 守护进程监听串口；
   - 短信实时写入 NAS SQLite/数字资产数据库，通过家庭宽带转推 MQTT/微信；
   - 宽带断网时，NAS 可自动指令板端开启 RNDIS，作为家庭网络的 4G 逃生通道。
3. **AI Agent MCP 蜂窝物理化拓扑 (AIR-06)**：
   - 基于 FastMCP 协议栈落盘 `tools/mcp_server/server.py`；
   - 外部 Agent（Claude Desktop / Cursor / 工作区 Agent）通过标准 stdio JSON-RPC 接入；
   - 暴露 7 大物理工具：`get_gateway_status`, `send_sms`, `get_latest_otp`, `get_sms_history`, `clear_sms_history`, `toggle_rndis`, `reboot_gateway`；
   - 使大模型拥有真实世界 4G 蜂窝射频物理收发与验证码主动提取能力。

## 6. Web 控制台体系与底层协议栈技术定论 (AIR-10)

针对图形化管理控制台的工程实现与硬件物理边界，系统完成了双 Web 体系架构探索与移芯芯片底层协议栈逆向实测：

### 6.1 宿主端 Web 管理控制台（核心主力入口）
- **实现载体**：`tools/host_gateway/gateway_web.py`（监听 `0.0.0.0:17801`，一键启动批处理 `run_web.bat`）。
- **架构优势**：
  1. **零 4G 蜂窝流量开销**：宿主端 Web 完全基于宿主机（PC/NAS）的本地回环网络（`127.0.0.1:17800` Hub）与物理串口通信，彻底杜绝 Windows 开启虚拟网卡可能产生的偷跑流量；
  2. **自包含极简响应式 SPA**：零 npm/webpack 依赖，纯原生现代 HTML5/CSS3/ES6 编写，深色玻璃拟态质感，完美适配手机、平板与桌面浏览器；
  3. **实时全双工无刷新感知**：基于 HTTP Server-Sent Events (SSE) 协议，新短信接收、验证码提取与来电拦截毫秒级推流渲染，支持一键点击复制验证码；
  4. **硬件与保号双重防御切换**：界面直观提供 4G 随身网卡（RNDIS）与板载蜂窝数据（0 流量保号）的一键受控切换开关。

### 6.2 板载内嵌 Web 方案技术定论与退役归档（彻底定论：单 USB 裸板无法直连）
- **技术定论**：
  在单根 USB 线连接的 Air780EPV 裸板形态下，**“浏览器直连板载内嵌 Web”在物理与固件驱动层面被证明彻底不可行**：
  1. **物理拓扑边界**：板卡无 Wi-Fi、无以太网 RJ45，宿主机与模组之间仅有一条 USB 复合设备链路（CDC 串口或 RNDIS 网卡）；
  2. **纯串口模式（日常 0 流量保号态）**：PC 侧无虚拟网卡，无法承载任何基于 TCP/IP 协议的浏览器 HTTP 流量；
  3. **RNDIS 网卡模式（FastPath 硬件直通旁路）**：
     逆向 `luatos.elf` 与硬件抓包证实，移芯 EC718PV 芯片在固件底层通过 `NetifUlPkgFastPath` (`0x41c404`) 与 `PsifDlPkgFastPath` 实现了驱动级硬件加速。RNDIS 开启后，PC 发出的流量直接穿透到基站 WAN 侧或在驱动层被丢弃，根本不经过板端内嵌 LwIP 协议栈的上层输入处理，导致 PC 无法与板载 `httpsrv:80` 完成 TCP 三次握手；
  4. **体验与单片机资源严重劣化**：
     由于板载 Flash 上限仅 64KB，嵌入在 Lua 脚本内的 HTML 模板被极度压缩（<6.5KB），导致排版简陋拥挤、交互体验极差，与现代控制台形成巨大反差；同时额外占用了 10KB 宝贵的 Lua 运行堆内存与 6KB Flash 存储。
- **工程退役与裁剪决策**：
  - 彻底下线并从板载固件 Flash 中剔除 `web_service.lua`，回退网关固件至轻量纯净版，回收 10KB 运行 RAM 与 6KB 存储 Flash，单片机常驻堆内存降至 66KB（空闲率 48.4%）；
  - 将所有本地 mock 脚本（如 `preview_embedded_web.py`）及临时预览页面全部安全移入系统回收站；
  - 固化相关协议栈逆向分析、FastPath 旁路原理与避坑结论。
- **系统唯一权威架构入口**：
  **统一由宿主端 Web 管理控制台（端口 17801）作为核心图形化管理面板**，通过物理串口多路复用中枢（Hub）与网关模组通信，既享有现代化高颜值深色面板与毫秒级 SSE 推流，又坚决守住绝对 0 蜂窝流量与高可靠性的物理底线。

针对网关在分发体验、多设备扩展、前端实时刷新、剪贴板交互以及多板硬件互联等 5 大核心演进课题，系统确立如下事实规范与工程演进标准：

### 7.1 软件分发与串口自适应探测架构（课题 1）
- **现象与问题**：
  上位机早期开发时曾硬编码 `SERIAL_PORT = "COM8"`。当软件分发给其他用户或设备拔插/复位漂移（如漂移至 `COM16`）时，写死 COM 口会直接导致上位机启动连不上硬件。当前已全面落地动态探测与自愈引擎。
- **Air780EPV 硬件串口特征**：
  - USB 厂商与产品 ID：`VID = 0x19D1, PID = 0x0001`（合宙/移芯官方 CDC-ACM 复合设备）；
  - 单个物理硬件在 Windows 下复合枚举出 **3 个独立虚拟串口**：
    1. `LOCATION=...x.2`：AT/日志口；
    2. `LOCATION=...x.4`：AP/调试口；
    3. `LOCATION=...x.6`：用户通信与虚拟串口（映射到 LuatOS `uart.VUART_0`）。
- **工程解法规范**：
  1. **双层自动扫描探测引擎**：
     - 第一层：通过 `serial.tools.list_ports.comports()` 遍历系统可用串口，基于 `VID=0x19D1, PID=0x0001` 自动圈定合宙模组候选端口列表；
     - 第二层：对候选端口发送非阻塞轻量探测帧 `{"type":"cmd","cmd":"ping"}` 或监听特征 `status` 心跳，自动锁定响应 NDJSON 协议的通信口；
  2. **手动指定与配置持久化**：
     - 在 Web 控制台设置抽屉中提供“串口选择”下拉列表（含“自动探测（推荐）”及所有已枚举 COM 口选项）；
     - 用户手动选定的端口自动持久化至 `gateway_config.json`，下次启动优先尝试历史成功端口。

### 7.2 验证码自动复制开关与防打扰规范（课题 2）
- **现象与设计意图**：
  当前上位机（Hub 与 Web）一旦提取到验证码短信，无条件毫秒级直写 Windows 系统剪贴板。该设计虽极致提速，但存在侵入性风险：若用户刚复制了一段核心代码或复杂长文本，突发短信会冲刷剪贴板导致用户原复制内容丢失；同时在投屏、远程会议或多设备剪贴板同步（如 Win+V 云同步）场景下存在隐私泄露隐患。
- **工程解法规范**：
  1. **配置项显式化**：在 `gateway_config.json` 引入 `system.auto_copy_otp`（布尔型，默认 `true`）；
  2. **前端交互与说明**：Web 控制台设置抽屉提供“⚡ 验证码自动写入系统剪贴板”切换开关，并附带体验说明：“开启后捕获验证码直接 Ctrl+V 即可粘贴；关闭后仍可随时点击短信卡片上的复制按钮手动取码”；
  3. **双端双向响应**：
     - 后端 `gateway_hub.py` 在执行 `set_windows_clipboard` 前核验配置项，若关闭则仅推送 Toast 提示而不写入剪贴板；
     - 前端 `web/index.html` 在 SSE 收到 `sms_received` 时，同样仅在开关激活时调用浏览器剪贴板 API。

### 7.3 实时数据流与前端渲染类型容错规范（课题 3）
- **现象与致命根因**：
  用户反馈“短信来了之后上位机好像不会自动刷新”。经排查定位到确切的隐蔽运行时崩溃：
  1. 板端 `sms_service.lua` 发送的实时事件包中，`time` 字段直接取了 `os.time()`（整型时间戳，如 `1726136800`）；
  2. `gateway_web.py` 在接收 `sms_rx` 并向 SSE 广播时，直接透传了该整型数字，未做格式化转换；
  3. `web/index.html` 的 `renderSmsList()` 在排序时执行 `tB.localeCompare(tA)`。当 `tB` 为整型数字时，JavaScript 抛出致命错误：`TypeError: tB.localeCompare is not a function`；
  4. 异常被外层 `catch (err) {}` 静默吞掉，导致 DOM 渲染彻底阻断，新短信无法展示，造成“无法自动刷新”假象。
- **工程解法规范**：
  1. **后端数据标准化**：`gateway_web.py` 在转发 `sms_rx` 时强制将时间字段标准化为 `YYYY-MM-DD HH:MM:SS` 格式字符串；
  2. **前端防御性转换**：`web/index.html` 所有时间比较强制使用 `String(tA || '')` 防御，避免非字符串调用 `localeCompare`；
  3. **禁止空 catch 吞异常**：显式打印控制台错误日志，保障数据流可观测性。

### 7.4 多设备接入架构设计（课题 4）
- **物理与操作系统事实**：
  多块 Air780EPV 同时通过 USB 接入电脑时，每块板子拥有独立的 USB 控制器与序列号，Windows 会分别枚举出独立的串口组（板A=COM6/7/8，板B=COM9/10/11）。彼此在物理层、电气层与操作系统驱动层完全隔离，天然支持同时并发通信，互不干扰。
- **多设备会话池架构演进（Device Session Pool）**：
  1. **多端口并发管理**：上位机 Hub 升级为设备会话池，为每个检测到的模组分别维护一个 `GatewayDeviceSession`，通过 SIM 卡 `ICCID` 或模组 `IMEI` 作为唯一硬件标识（Device ID）；
  2. **数据资产汇聚与打标**：短信入库与通知分发打上 `device_id` 与 `sim_slot` 标签（例如“卡1·联通 132****”、“卡2·移动 138****”）；
  3. **双模式 Web 界面**：
     - **聚合信息流（All-in-One）**：双卡/多卡短信按时间倒序混排，卡片标注来源设备专属色块；
     - **设备切换器**：顶栏支持切换当前控制的目标设备，独立查看该卡的信号 RSRP、温度、电压、RNDIS 网卡与 FOTA 升级状态。

### 7.5 硬件堆叠电气评估与最优工业拓扑（课题 5）
- **排针直通上下焊接之致命风险（坚决禁止）**：
  Air780EPV 两侧排针引出 `5V`、`V_GLOBAL_3V3`、`UART_TX/RX`、`PWRKEY` 等核心信号。如果直接点对点上下堆叠焊接：
  1. **电源反灌烧毁**：各板内部 DCDC/LDO 产生的 3.3V 存在微小工艺压差（如 3.31V 与 3.29V），直接直连会引发持续的无保护倒灌电流，烧毁电源芯片；
  2. **串口对地短路击穿**：若板 A 的 TX 与板 B 的 TX 短接，当两板逻辑电平相反时（高电平 3.3V 对 低电平 0V），将形成电源对地直通短路，击穿芯片 GPIO 推挽管；
  3. **按键控制丧失独立性**：PWRKEY 直通将导致两块板子强制同步开关机，无法单独复位。
- **最优工业级解法：带供电 USB 集线器 + 立式刀片卡架**：
  - **硬件构成**：采购工业级带独立 12V 供电的 4~7 口 USB Hub，每块 Air780EPV 采用超短直角 Type-C 数据线插入，搭配亚克力或 3D 打印立式卡架垂直插放；
  - **核心优势**：
    1. **零硬件修改**：保留所有开发板完整原生形态与质保，零短路风险；
    2. **独立热插拔**：更换任意 SIM 卡或单板烧录维护，其他板卡零中断运行；
    3. **高速 USB 隔离**：走 USB 2.0 原生独立总线中断，吞吐量远胜脆弱的板间低速 I2C/串口；
    4. **供电稳定充裕**：独立电源可轻松支撑多路模组同时发射时的高达 1A 峰值脉冲电流。

## 8. 宿主宽带代推优先与 Push ACK 超时降级容灾架构 (AIR-17)

### 8.1 架构设计背景与 0 流量保号防线
出厂状态下，网关遵循“0 流量纯信令保号”原则，板载蜂窝数据通信严格掐断（`mobile.data(mobile.CONF_CELLULAR_DATA, 0)`）。日常所有飞书、Bark、Webhook 推送均由宿主机（PC/NAS）通过本地宽带代推。
然而，若电脑休眠、断电或网关程序意外退出，新短信可能因宿主失联而无法送达。系统确立**“宿主宽带优先代推 + Push ACK 握手确认 + 5秒超时板端降级自推 + 离线黑匣子兜底”**的四级闭环：

### 8.2 双向握手与时序流转
1. **事件抛出**：板端收到新短信时，通过 VUART_0 物理串口向宿主机抛出主动推送帧：
   ```json
   {
     "type": "push",
     "event": "sms_received",
     "data": {
       "msg_id": "sms_1726160000_1234",
       "phone": "+8613800000000",
       "content": "【某某平台】验证码：123456",
       "otp": "123456",
       "time": 1726160000
     }
   }
   ```
2. **守候定时器挂起**：板端调用 `sys.timerStart(timeout_cb, 5000, msg_id)` 启动 5.0 秒软件看门狗，并置位待确认状态；
3. **宿主机宽带代推与回执**：
   - 宿主机 Hub 监听到 `sms_received` 事件后，立即通过本地局域网/宽带代发飞书 Webhook 或 Bark；
   - 无论代推成功与否，宿主机立即向物理串口回送专属 Push ACK 帧：
     ```json
     {"type": "push_ack", "event": "sms_received", "msg_id": "sms_1726160000_1234"}
     ```
4. **板端握手确认与定时器取消**：板端 `serial_comm.lua` 收到该 ACK 后，校验 `msg_id` 一致，立即调用 `sys.timerStop` 销毁定时器。全程未开启蜂窝数据，流量消耗为 0；
5. **宿主失联与板端降级自愈**：
   - 若 5.0 秒内未收到 ACK（宿主机离线），`timeout_cb` 被触发；
   - 板端自动执行“临时使能蜂窝数据（`mobile.data(mobile.CONF_CELLULAR_DATA, 1)`）➔ 驻网检查 ➔ 板端 HTTP 直推 Webhook ➔ 推送完成立刻切断蜂窝数据”的原子自愈流程，守住短信不丢失的高可用生命线。

## 9. 来电暗号拦截秒挂与七牛云空中热更新 FOTA 标准 (AIR-18)

### 9.1 来电暗号：0 话费纯信令拦截秒挂 (`call_service.lua`)
- **秒级拦截算法**：注册 `sys.subscribe("CC_IND", ...)`。基站呼入到达模组触发 `RING` 振铃状态时，微内核在毫秒级内直接调用 `cc.hangUp()` 切断通话；
- **0 话费保障**：呼叫尚未接通即被挂断，运营商基站无法建立计费会话，通话账单为 0 元；
- **暗号联动 FOTA**：比对呼入主叫号码，若匹配 `config.lua` 中预设的管理员白名单（`secret_caller`），板端自动触发静默 FOTA 升级任务。

### 9.2 七牛云空中热更新（FOTA）底层容器规范
板端基于七牛云华东 CDN（`z0` 空间，域名 `http://raw-fota.air780epv.luat.com.cn` 或配置镜像源）执行免插线固件热更新：
- **92 字节标准 LuatOS OTA 头部**：
  LuatOS 底层 C 固件拒绝直接刷写纯文本 Lua 压缩包。升级镜像（`update.bin`）前 92 字节必须填充标准二进制头：
  - Magic 标识（4 字节，如 `0x54414F4C` 即 `LUAT`）；
  - 硬件平台识别码（EC718PV / EC618）；
  - 固件版本号与镜像长度；
  - CRC32 校验和与数字签名占位。
- **LZMA SOTA 压缩容器**：
  核心代码段采用 LZMA 算法高压缩比封装，确保升级包体积被严格压缩在 Flash OTA 预留扇区（< 32KB）之内；
- **上位机构建发布流水线 (`tools/fota/publish_ota.py`)**：
  自动读取 `deploy/smart-gateway-780epv/` 下各 Lua 源码，调用原生 LuaDB 打包器生成紧凑二进制，注入 92B Header 与 LZMA 容器，计算 SHA256，生成 `version.json`，并一键推送到七牛云对象存储空间。

## 11. 串口自适应动态探测与热拔插漂移自愈机制

### 11.1 串口漂移痛点与根因
模组在复位、烧录固件或拔插后，Windows USB 枚举可能将端口由 `COM8` 漂移至 `COM16`（或者 `COM6` 漂移至 `COM15`）。若上位机硬编码串口号，将导致服务瘫痪。

### 11.2 动态特征探测引擎 (`find_cellular_vuart_port`)
上位机通过 `serial.tools.list_ports.comports()` 读取系统枚举树，匹配物理拓扑：
1. **硬件 ID 圈定**：匹配 `VID:PID == 19D1:0001`（合宙/移芯复合设备）；
2. **接口拓扑精准过滤**：
   - 过滤 `LOCATION` 包含 `x.4` 的 Trace 调试口（避免非文本二进制流使程序崩溃）；
   - 过滤 `LOCATION` 包含 `x.2` 的 AT 口；
   - 锁定包含 `x.6` 或 `MI_06` 的 **VUART_0 用户口**（无论其被系统重命名为 COM8 还是 COM16）。
3. **断线热扫描自愈**：
   Hub 主循环捕获 `SerialException` 后，立即释放句柄并以 1.5 秒为周期循环重试探针。设备重新插入后秒级重新建链，上层 SSE 推流与 Web 客户端完全透明无感。

## 12. 黑匣子三层防 OOM 游标分页与前端触底无感懒加载

### 12.1 连续刷新导致的板端 OOM 重启根因
Air780EPV 板载 Lua 堆内存上限仅 128KB。当脱机黑匣子积累数十条短信时，若上位机 Web 控制台并发或连续刷新，板端连续执行全量 JSON 序列化将瞬间耗尽可用堆（OOM），引发芯片硬件看门狗硬重启。

### 12.2 三层游标分页架构
- **板端游标协议**：
  游标设计为 `h:<generation>:<offset>`（如 `h:36:15`）。板端每次最多切片返回 15 条记录，单条正文强力截断至 256 字节，内存峰值恒定控制在 12KB 以内；
- **后端有效性清洗防御 (`gateway_web.py`)**：
  前端 Web 页面由于异步竞争可能传进 `"0"`、`"null"`、`"undefined"` 等非预期游标。后端在调用 Hub 之前进行正则白名单校验：仅格式合法的游标透传给板端，非法游标一律清洗为空（按首屏最新 15 条处理），彻底避免板端正则匹配失败报 `CURSOR_STALE` 甚至崩溃。

### 12.3 前端无感懒加载双保险设计
- **触发感知**：收件箱底部挂载 `#smsSentinel` 哨兵节点，通过 `IntersectionObserver` 配合 `rootMargin: '160px'` 预先拉取；
- **确定性判定三步法**：
  1. 优先校验后端显式返回的 `has_more` 布尔值；
  2. 其次校验 `next_cursor` 是否非空；
  3. 再次比对 `total > 当前卡片数`；
- **零增量死循环熔断**：非首屏请求下，若拉取到的增量短信数量为 0，立即熔断置 `smsHasMore = false` 并展示“已加载全部脱机记录”，彻底消除网络死循环风暴。

## 16. 硬件未接入/离线状态防震荡与 Fast-Fail 机制 (AIR-15 缺陷根治)

针对上位机在未插入 4G 短信棒时出现的“已连接 / 已断开”红绿 Toast 震荡、4000ms 挂起超时与假在线缺陷，系统落地端到端全链路闭环架构：

### 16.1 根因剖析与防御时序
1. **中枢无阻塞 Fast-Fail 机制**：
   - 传统逻辑在物理串口未打开时直接丢弃客户端下发的命令，导致 Web 层等待 RPC 响应直至 4.0 秒硬超时；
   - 修复后：中枢 `gateway_hub.py` 在串口未连接或离线时，立即向客户端回送 `{"type": "response", "id": req_id, "ok": false, "online": false, "error": "4G 短信棒未插入或物理串口已断开"}`，请求在 0~1ms 内极速返回，杜绝 Web 服务端线程阻塞。
2. **状态快照严格清洗与归零**：
   - 物理串口断开或未接入时，Hub 与 Web 两级内存缓存的工况数据（CSQ、RSRP、温度、供电、运行时间等）强制清洗为初始占位符，且核心元数据坚决标注 `"online": false`；
   - 杜绝向 Web 前端下发残留旧快照，彻底消除了旧快照伪装在线与看门狗判定打架的死循环。
3. **前端状态机确定性判定**：
   - 前端 `renderStatus()` 升级为强类型断言，仅当 `data.online === true` 时才允许切为在线态；
   - 设备切为离线态时立即将 `state.lastHeartbeatTime` 彻底清零，杜绝因异步心跳轮询回包导致时序倒流；
   - 优化断开 Toast 策略：仅当此前明确处于在线状态（`wasOnline === true`）时才弹出断开红框，初次打开或持续未插入状态静默保持离线，零假连接干扰。

## 17. 跨芯片（EC618 / EC718PV）大一统通信与开机主动握手探针机制

针对多硬件形态（Air780E/EC 基于移芯 EC618，Air780EPV 基于移芯 EC718PV）在冷启动、未插 SIM 卡或弱网搜网场景下的在线判定，系统落地如下工业级闭环规范：

### 17.1 跨芯片架构兼容性事实
1. **统一串口抽象**：
   - 移芯 EC618（Cortex-M3）与 EC718PV（Cortex-M4F）在 LuatOS 体系下均统一定义 `uart.VUART_0` 为 PC 端 USB 用户通信口（宿主机通常映射为 `COM8` 或漂移后的 `COM16`）；
   - 网关协议统一基于 `uart.VUART_0` 发起 JSON RPC，全双工零丢包，无需任何特定硬件平台私有逻辑分支。
2. **消灭握手死锁与被动等待陷阱**：
   - **历史缺陷**：模组固件开机时仅在 `SIM_IND == "RDY"`（SIM 卡驻网就绪）后才发送首帧 `gateway_ready`；若用户未插入 SIM 卡，板端陷入绝对静默。而宿主机上位机 Hub 打开串口后仅被动执行 `readline()` 等待首帧才建立业务在线。双方互相死等，导致未插卡时上位机误判为“设备已断开”；
   - **双向自愈防线**：
     - **板端保底就绪首帧**：`deploy/smart-gateway-780epv/main.lua` 在开机 2.0 秒后无条件向串口发射 `gateway_ready` 首帧（即使未插卡也能带上真实的 CPU 温度、供电电压、芯片型号与固件版本）；当后续 SIM 卡插入或完成驻网（`SIM_IND == "RDY"`）时，再次触发增量状态通知；
     - **上位机主动握手探针 (Active Handshake Probe)**：中枢守护线程在打开物理串口后，若处于未确认连接态，每隔 1.5 秒温和下发一次轻量 `ping` 探针（`{"type":"cmd","id":"hub_probe_handshake","cmd":"ping"}`）；板端在 10ms 内回复 `pong` 响应包，Hub 捕获到首个合法 JSON 帧瞬间立即确立业务在线并全网广播 `device_connected`。
   - **实测表现**：Air780EC（EC618）插入即自动秒级点亮，Web 控制台精准呈现 `无 SIM 卡`、`无网络信号`、`核心 34.0 ℃`、`供电 4.09 V`，常用防偷跑开关均正常生效。

## 18. 短信连续发送协议终态与死锁修复架构 (AIR-25)

### 18.1 缺陷场景与底层根因剖析
在真机自动化与 NAS 插件应用现场中，用户反馈发送首条短信成功后，再次发送会必定失败并提示“发送失败: 发送短信超时”。系统深挖出三层缺陷：
1. **板端假死锁陷阱**：板端 `sms_service.lua` 使用了 60 秒定时器等待 `SMS_SENT` 事件解冻状态机。经逆向 LuatOS 符号表与固件代码确认，底层 C 内核并未实现向 Lua 广播 `SMS_SENT`，`sms.send()` 返回 `true` 即代表已进入底层基站发射队列。板端在 60 秒到期后必定引爆看门狗将 `sms_frozen` 置为 `true`，致使后续所有发信直接被拒绝返回 `-409 SMS_RESULT_UNKNOWN`；
2. **上位机首帧提前出队造成终态丢失**：`gateway_web.py` 在首帧收到 `code: 0, msg: "QUEUED"` 受理帧时，就提前从 `pending_requests` 字典中弹出了该请求 ID，导致后续该请求的真正终态（`SENT_OK` / `SENT_FAILED` / `UNKNOWN`）全部无法路由；
3. **错误原因被泛化掩盖**：上位机 HTTP 路由只检查 `resp.get("error")`，未能提取 `-409`、`-429`、`-102`、`-1` 等标准业务码和 `data.reason`，直接兜底返回“发送短信超时”，掩盖真实错误。

### 18.2 闭环架构与工程规范
1. **板端发射窗口保底与自愈推进**：
   - 移除 60s 必爆自锁定时器，在 `sms.send()` 提交成功并回送首帧 `QUEUED` 后，启动 2.5 秒基站空口发射窗口定时器；窗口到期时自动回传 `code: 0, msg: "SENT_OK", data: {success: true}`，重置 `active_tx` 与 `sms_frozen`，并自动调用 `dispatch_next()` 消化后续排队短信；
   - 保持对底层前向兼容的 `SMS_SENT` 监听，若提前收到则取消定时器立即终态回执；
   - 新增 `reset_sms` / `clear_sms_queue` 串口与 Web API 远程强制解冻复位指令。
2. **上位机终态等待（wait_terminal）与错误精准映射**：
   - `execute_cmd` 引入 `wait_terminal=True` 选项；在分发帧处理中，对等待终态的请求，收到受理帧 `QUEUED` 仅推送 SSE 广播与记录标记，不移除待决字典；直到捕获到终态帧才正式唤醒并返回；
   - 实现 `_format_error_message(resp)`，精准映射 `-409`（上一条短信未决，设备保护中）、`-429`（短信发送队列已满）、`-101`（参数错误）、`-102`（模组射频发射失败）、`-1`（基站发送失败）等中文说明。
3. **前端文案分级**：
   - 区分 `queued`（已送达基站发射队列）与 `sent`（短信已成功发出！）；
   - 错误弹窗完整呈现服务端返回的精确中文原因。

## 19. 硬件型号自适应与多卡槽唯一标识溯源规范 (AIR-26)

### 19.1 背景与设计动机
在多板卡集群或混合设备部署场景下，此前系统存在以下标识缺陷：
1. **静态设备名陷阱**：板端脱机 4G 自推 (`notify_service.lua`) 与上位机本地代推 (`gateway_hub.py`) 底栏写死了固定的 `设备ID: Air780EPV`；当用户接入 Air780EC、Air780E 时，无法反映真实硬件芯片；

3. **USB 端口漂移对账难**：仅依赖临时分配的 COM 端口（如 COM7 拔插后变为 COM8），缺少物理层全球唯一硬件指纹（IMEI / 芯片 UID）作为定址锚点。

### 19.2 架构实施与分层规范
1. **模组固件层 (`deploy/smart-gateway-780epv/`)**：

   - **串口帧全面丰富**：在 `STATUS_OK`、`gateway_ready`、`sms_rx`、`call_rx`、`state_change` 中统一携带 `model`, `bsp`, `imei`, `iccid` 字段；
   - **脱机直推底栏动态化**：`notify_service.lua` 废除硬编码，格式化为 `设备: {model} (IMEI: {imei}) （4G蜂窝直推）`。
2. **上位机推送中枢 (`tools/host_gateway/` & `tools/cluster_gateway/`)**：
   - **设备溯源底栏标准规范**：
     - 单卡模式：`设备: {model} · IMEI: {imei} （电脑本地宽带代推）`；
     - 集群多卡模式：`设备来源: [{slot_id}] {model} · IMEI: {imei} （电脑本地宽带代推）`；
   - **多渠道全适配**：飞书 Schema 2.0 交互卡片 Footer、企业微信 Markdown、钉钉 Markdown、iOS Bark（按型号分组）与通用 Webhook 统一输出结构化硬件来源信息；

3. **Web 控制台前端与卡槽对账**：

## 20. 数据全生命周期闭环与多卡分舱运维架构 (AIR-27)

### 20.1 痛点背景与根因分析
在网关持续运行与多卡槽演进过程中，用户与业务系统暴露了以下关键数据与运维痛点：
1. **单条删除数据“死而复生”**：上位机收件箱单条删除仅修改了内存列表；当用户点击刷新时，因板端 LittleFS 黑匣子未同步删除，被删短信再次被拉取呈现；
2. **多板多卡混插数据串台**：用户更换 SIM 卡或轮插不同模组时，所有短信混存在一个扁平的 `gateway_history.json` 中，缺乏基于 SIM 卡身份（ICCID）的物理隔离与专属墓碑；
3. **Flash 擦写磨损与隐私泄露担忧**：板端默认无条件写入 LittleFS，长期高频短信加速 Flash 磨损，且拔下插棒后芯片内残存历史短信；
4. **收件卡槽身份盲区**：Web 控制台短信卡片仅展示发件人号码与时间，无法直观辨识是由哪张 SIM 卡接收，缺乏类似双卡手机的运营商与卡槽气泡；
5. **开机未插卡静默与误报**：开机未插卡时不触发驻网信令，若上位机未作超时探针会导致静默无知；若开机瞬间盲目外推又会产生假警报。

### 20.2 架构实施与技术规范
1. **强确定性原生 msg_id 墓碑防复活引擎 (`storage_manager.py`)**：
   - **主键确定性**：摒弃有冲突风险的时间桶散列算法，直接采用板端原生全局唯一不可变 `msg_id`（格式形如 `boot_{seq}_{time}_sms_{seq}`）作为对账主键；历史遗留无 ID 记录回退采用精确实体哈希 `MD5(f"{iccid}:{from}:{content}:{raw_time}")`；
   - **结构化墓碑**：在 `cards/{ICCID}/tombstones.json` 中独立维护被删短信实体；
   - **静默过滤防复活**：上位机在从板端 LittleFS 拉取历史或接收实时帧时，经墓碑过滤器瞬间剔除已删条目，100% 杜绝因时钟漂移导致的死而复生，且绝不误杀同一分钟内的重复验证码。
2. **模组闭环确认（Store ACK）与 0 磨损安全兜底 (`sms_service.lua`)**：
   - 收到短信中断 `SMS_INC` 时，若开启仅存上位机（`store_on_board == 0`）且物理串口在线，板端先不写入 LittleFS，将短信暂存 Lua 内存并通过 `sms_rx` 发送给上位机，同时启动 **3.5 秒保底定时器**；
   - 上位机落盘成功后回发 `sms_store_ack` 串口帧，板端注销定时器并销毁内存暂存，**达成物理级真·0 Flash 磨损与防隐私残留**；
   - 若脱机插座运行导致 3.5 秒内未收到 ACK，定时器触发自动降级写入 LittleFS 黑匣子，**达成 0 丢件底线保障**。
3. **ICCID 物理分舱与受管双写兼容**：

## 21. 上位机一键固件写入与升级双轨架构规范 (AIR-21)

### 21.1 痛点背景与设计目标
在 AIR-21 之前，固件写入与脚本更新长期依赖合宙官方 80MB 的 Luatools 客户端，面临严峻挑战：
1. **黑盒臃肿与 GUI 强依赖**：每次改动业务代码，开发者或用户必须手动打开 Luatools GUI 窗口或编写脆弱的 Win32 鼠标坐标模拟点击脚本，极易受屏幕分辨率、DPI 缩放和窗口遮挡影响；
2. **缺乏代码级自动化能力**：上位机软件与 AI Agent 无法通过程序化 API 对模组下发版本更新，无法实现“改完代码一键推送生效”的现代化 DevOps 体验；
3. **出厂初刷与日常热更混淆**：把几 KB 的应用层 Lua 脚本改动等同于底层重刷，每次更新都要强行重启进 ROM Bootloader，耗时长且存在端口抢占风险。

### 21.2 双轨升级技术架构
针对不同应用场景，AIR-21 确立并落地了“日常热更”与“物理初刷/救砖”双轨分层体系：

```
                    ┌───────────────────────────────────────────────┐
                    │            上位机一键升级中心 (Web/Hub)       │
                    └──────────────────────┬────────────────────────┘
                                           │
                    ┌──────────────────────┴──────────────────────┐
                    ▼                                             ▼
       【模式 A：日常极速热更 (首选)】              【模式 B：移芯无头物理烧录 (出厂/救砖)】
  • 纯 Python 语法预检与标准 LuaDB 打包        • 免物理按键，AT 软复位进 Bootloader
  • 封装 SOTA 升级容器 (92B CoreUpgrade 头)    • 移芯原厂无头 FlashToolCLI.exe 静默调起
  • USB 控制串口分块流式灌入 (Base64)          • 物理端口让渡协议 (pause_serial / resume)
  • 模组片上扇区直写校验，3 秒无感更新         • 写入 Flash 0x00324000 扇区，实时解析进度
  • 0 网络 IP 拓扑依赖 (免 RNDIS/127.0.0.1)     • 30s 硬看门狗超时自愈与 423 互斥写锁
```

### 21.3 核心技术突破与工程实现
1. **纯 Python LuaDB 虚拟文件系统生成器 (`tools/host_gateway/luadb_packer.py`)**：
   - **前置语法预检**：打包前静态扫描 11 个核心 Lua 脚本的词法与括号匹配，杜绝因语法错误导致模组反复重启（Reboot Loop）；
   - **合宙标准 LuaDB 二进制封装**：精确实现 TLV 根头（24 字节，Magic `01 04 5a a5 5a a5`，长度声明 `0x18`）、各文件条目对齐与尾部 16 字节 `.airm2m_all_crc#.bin` MD5 校验文件；
   - **标准 SOTA 容器生成**：支持调用官方 `soc_tools.exe` 生成带有 92 字节 `CoreUpgrade` 头（Magic `0xeac37218`）、目标基址 `0x00324000` 与尾部 CRC32 校验的标准升级包。
2. **串口分块流式热更机制 (`fota_service.lua` & `gateway_web.py`)**：
   - **分块握手协议**：上位机下发 `ota_start` 协商包大小与 MD5，通过 `ota_chunk` 循环下发 2048 字节分块（Base64 编码，彻底避免 `0x0A` 截断 JSON 帧），最后下发 `ota_finish` 触发固件片上 Flash 直写与校验；
   - **极速软复位加载**：整套应用层热更在 3 秒内完成，校验成功后模组自发软重启加载最新逻辑。
3. **物理端口让渡协议与移芯无头物理烧录 (`firmware_flasher.py` & `gateway_hub.py`)**：
   - **Bootloader 端口隔离**：修改 `gateway_hub.py`，将 `VID 17D1: PID 0001`（移芯 Bootloader 端口）从常规业务通信端口扫描中彻底剔除，避免 Hub 争抢句柄导致 WinError 5；
   - **端口让渡强保 (Port Yield Protocol)**：烧录启动前下发 `pause_serial` 命令使 Hub 关闭串口并暂停重连；烧录完毕后在 Python `finally` 块中无条件调用 `resume_serial` 恢复中枢监听；
   - **无头驱动 FlashToolCLI**：通过 `AT+ECRST=delay,599` 触发免按键进 Bootloader，静默调起移芯原厂 `FlashToolCLI.exe -p {port} --cfgfile config_pkg_product_usb.ini burn`，实时正则匹配标准输出提取 0%~100% 进度推流。
4. **全局烧录互斥写锁与毛玻璃可视化交互 (`web/index.html`)**：
   - **全局互斥锁 (423 Locked)**：烧录期间所有可能干扰设备状态的控制请求（重启、发短信、清空等）统一被 HTTP 423 拦截，并设 60 秒看门狗超时自愈，杜绝死锁；
   - **分级抽屉与毛玻璃流式进度模态窗**：设置抽屉清晰呈现“模式 A 串口热更”、“模式 B 移芯物理烧录”与“模式 C 脱机空中 FOTA”；点击后调起全屏毛玻璃流式进度弹窗，通过 SSE `flash_progress` 实时展示百分比与动态操作状态。

## 22. 短信转发集群多卡槽系统级支持架构规范 (AIR-22)

### 22.1 痛点背景与设计动机
在 AIR-19 中，系统实现了多板卡底层解耦与动态会话池（`DongleSessionPool`），但面对多卡物理集群部署与企业级聚合运维时，仍暴露以下核心短板：
1. **出站缺乏集群级智能路由与策略分流**：缺乏运营商同网识别、多卡轮询与信号最佳优选机制，多卡出站未发挥资费优化与分流优势；
2. **在飞超时并发重发的双扣费隐患**：在 4G 蜂窝网络基站延迟下，未决状态下盲目跨卡 Failover 重发极易引发双重发信与资费多重扣除；
3. **缺少全集群全局驾驶舱与跨卡聚合收件箱**：运维人员无法一眼纵览所有已接入卡槽的物理型号、信号强弱、工作温度及健康度；聚合查看历史短信时缺乏游标分页，存在全量加载引发内存 OOM 的严重风险；
4. **缺乏卡槽健康监控与防惊群断路器**：3GPP 规范瞬态 `CSQ: 99` 易引起惊群误判脱网，卡槽遭遇基站异常全降级时若缺乏紧急兜底将引发集群整体瘫痪。

### 22.3 核心技术突破与工程实现
1. **ClusterRouter 智能出站路由调度 (`tools/cluster_gateway/cluster_router.py`)**：
   - **手机号码标准化清洗与四大运营商前缀识别**：自动剥离 `+86`/`0086`/空格/连字符，支持移动（134~139/147/150~152/157~159/172/178/182~184/187~188/195/197/198）、联通（130~132/145/155~156/166/175~176/185~186/196）、电信（133/149/153/173/177/180~181/189/190~191/193/199）、广电（192）及 170/171/162/165/167 虚拟运营商精准识别；
   - **四大路由策略实现**：
     - `operator_affinity`（同网亲和优先，默认推荐）：根据手机号自动优选同网健康卡槽，无同网卡平滑降级至 `signal_best`；
     - `round_robin`（平滑轮询）：维护自增互斥指针在健康卡槽间均匀轮换；
     - `signal_best`（强信优先）：自动调度 CSQ 最高且健康的卡槽；
     - `direct`（定向直发）：死守隔离铁律，指定目标 slot 离线或熔断时坚决报错（`TARGET_SLOT_UNAVAILABLE`），严禁自动跨卡串号。
   - **In-flight 安全保护与 Failover 准入红线**：若指令已送达硬件处于等待基带/基站终态（`in_flight=True`），严禁盲目跨卡重试，杜绝基站延迟入网导致的多发多扣费；仅限前置离线与确定性错误允许 Failover；
   - **Panic Threshold 全熔断紧急兜底**：当遇到天线受损或基站大面积波动导致集群所有卡槽全降级或全熔断时，自动激活尽力而为兜底通道，按 CSQ 最高排序尝试发射，杜绝全集群瘫痪硬报错。
2. **ClusterHealthMonitor 卡槽健康与断路器自愈状态机 (`tools/cluster_gateway/cluster_health.py`)**：
   - **3GPP AT CSQ 99 防惊群去抖动**：对开机驻留或切网瞬态的 `CSQ: 99` 设置 10 秒/连续 3 次防抖门槛，过滤单次瞬态抖动，杜绝误熔断；
   - **三态断路器流转**：
     - `Healthy`：CSQ ≥ 10 且连续失败 = 0；
     - `Degraded`：5 ≤ CSQ < 10 或连续失败 = 2，移出自动路由池，仅限手动定向；
     - `Isolated`：连续失败 ≥ 3 或持续脱网，完全断路熔断；
     - `Half-Open`：进入 Isolated 满 60 秒冷却后转为半开态，允许单次试探复活，试探成功即恢复 Healthy。
3. **防 OOM 复合游标聚合分页与全集群 Web 驾驶舱 (`tools/cluster_gateway/web/index.html` & `gateway_web.py`)**：
   - **复合游标分页接口 (`/api/cluster/messages`)**：延续单批上限 15 条规范，基于时间戳与多卡分舱（`storage/cards/{ICCID}/`）实现多路倒序增量归并与 `has_more`/`next_cursor` 游标切片，杜绝多卡多条场景下的内存暴涨与 OOM；
   - **全集群全局驾驶舱 (Cluster Dashboard)**：主界面网格化呈现各卡槽型号、IMEI、SIM 运营商徽章、CSQ 信号柱、供电电压、核心温度、发信统计与健康状态徽章；
   - **聚合收件箱时间线**：短信卡片清晰展示 `[SLOT 1 · 移动 1234]` 等多卡彩色气泡徽章，支持点击徽章一键过滤单卡短信；
   - **出站策略发信弹窗**：弹窗支持直观选择四大出站策略与指定卡槽直发。

## 23. 单卡/多卡自适应统一网关 UI 架构与全量大白话交互规范 (AIR-28 UI Architecture)

### 23.1 架构演进背景与自适应哲学 (Single-Adaptive Gateway)
在以往的研发迭代中，上位机 Web 控制台经历了两代分裂割裂：
- **单机版控制台 (`tools/host_gateway/web/index.html`)**：左侧为单卡专属硬件工况卡片，右侧为单一短信列表；
- **集群版控制台 (`tools/cluster_gateway/web/index.html`)**：左侧为集群列表，右侧为聚合收件箱，需通过侧滑抽屉展示单卡详情。

这种“单机与集群双前端分治”的模式带来了代码重复、交互割裂以及用户在单卡与多卡切换时的割裂感。AIR-23 确立了 **“单卡/多卡自适应无感统一网关 UI 架构（Single-Adaptive Gateway Architecture）”**，其核心原则为：
1. **无感自适应 (Zero-Config Adaptation)**：同一套前端代码根据实际接入的物理模组数量（1 ~ N 块）自适应排版。插入 1 块板卡时，呈现极其精致优雅的单卡智能网关；插入 2~4 块板卡时，无缝扩展为多卡通信中枢，视觉心智完全一致。
2. **手风琴就地展开 (Accordion In-Place)**：彻底废弃右侧滑出的半透明半屏抽屉（Drawer）。所有卡片与模组的详细工况（信号、机身号、SIM 卡号、端口、温度、电压、开机时间、随身上网、升级与重启等）均在左侧卡片中**向下就地展开**，右侧通信流在任何操作下都保持 100% 完整可见，绝无遮挡。
3. **职责单点归敛 (Single Source of Control)**：彻底消灭全局设置与卡片局部控制的重叠。卡片的蜂窝移动数据、随身上网属于“单卡单控”属性，控制权 100% 归还给卡片本身；系统设置抽屉仅保留全局端口、5 大推送渠道与全局自愈偏好。
4. **生产与原型物理剥离与零闪烁契约 (Zero-Flicker First Paint via Physical Separation)**：原型归原型（完整独立保留于 `prototype_accordion_feed.html`），生产归生产（`tools/host_gateway/web/index.html`）。生产 HTML 中彻底物理拔除一切 `prototype-bar` DOM、演示模式胶囊、写死的假卡与假短信。初始静态 HTML 只保留纯净的真实单卡骨架与纯净空状态，浏览器初次绘制（First Paint）第 1 毫秒即是真实当前状态，从物理源头彻底消灭异步返回前的 FOUC 闪烁。
5. **Flex 弹性流贴底视口架构 (Viewport-Elastic Layout)**：彻底废除 `calc(100% - 92px)` 等一切硬编码高度计算，采用标准 Flexbox 视口伸缩流（`html, body { height: 100%; display: flex; flex-direction: column; }` 与 `main { flex: 1; min-height: 0; }`），确保工作台与两侧卡片在任何窗口尺寸（820px ~ 2K 全屏）下 100% 紧贴屏幕底部，底部黑色悬空真空死区彻底归零。

## 24. 短信双层存储模型与上位机大吞吐懒加载体系

### 24.1 嵌入式微内存硬约束与双层存储架构
EC618/EC718 运行 LuatOS 剩余可用堆内存仅 30~60KB，板端物理 LittleFS 空间与串口 TX FIFO 极小。若板端一次性吐出 100 条短信（约 25~40KB 纯文本 JSON 帧），将引发 LuatOS 内存溢出（OOM Panic）与串口环形缓冲区丢字节。因此确立**双层存储模型**：
1. **板端脱机缓冲黑匣子（板载 LittleFS）**：定位为脱机暂存，维持安全小批量单帧（15~20条）及 100 条循环覆盖上限，支持短游标分批读取；
2. **上位机权威持久化分舱（StorageManager）**：定位为永久权威存储，每个 ICCID 独立目录持久化，单舱容量扩充至 10,000 条。

### 24.2 后台异步收割与两阶段提交 (2PC) 清理防线
当模组插上或串口就绪时，上位机后台自动启动脱机收割工作流：
1. **循环分批收割**：上位机通过后台异步任务，以 `limit=15` 及短游标向模组请求脱机短信，循环往返拉取直至 `has_more=False`；
2. **落盘与原子持久化**：收割到的短信增量写入本地 ICCID 分舱 `messages.json`，并执行 `os.fsync` 确保落盘；
3. **两阶段提交 (2PC) 确认清理**：仅在本地落盘彻底成功后，上位机才向板端下发 `clear_history` 指令，板端 LittleFS 暂存即刻安全清零。断电时不丢信，重连时不重复收割。

### 24.3 复合稳定游标与服务端检索
1. **复合稳定游标 `(timestamp, id)`**：由于 LuatOS 时间戳精度为秒，同一秒若到达多条短信，单纯按时间戳截断会遗漏同秒短信。服务端采用 `"{timestamp}_{id}"` 复合游标，保证分页切片绝对稳定且不重不漏；
2. **服务端全局检索 (`keyword`)**：搜索下沉至服务端，直接对发件人与正文进行全局大小写无关匹配，彻底解决纯前端 DOM 隐藏导致“未加载的更早短信不可搜”的痛点；
3. **本地毫秒级即时响应**：前端短信列表查询 100% 走上位机权威存储，无需等待物理串口排队与空中传输延时。

### 24.4 Web 控制台 40 条大页首屏直出与 IntersectionObserver 懒加载
1. **首屏 40 条大页直出**：默认首屏拉取 40 条记录，视觉饱满丰富，无需频繁等待；
2. **200px 视口预加载**：底部部署轻量哨兵元素 `#smsFeedSentinel`，结合浏览器原生 `IntersectionObserver`，在用户距离底端 200px 时静默发起下一页预拉取，实现如丝般顺滑的“无感触底加载”；
3. **全生命周期墓碑标记**：前端单条删除时向服务端传递完整元数据并落盘墓碑记录，彻底杜绝已删除短信复活。

### 25.5 物理串口与短信发射避让机制
1. **串口指令精简防溢出**：Hub 下发 `send_sms` 时彻底剔除路由调试元数据，下发极简 JSON 帧（仅 `phone` 与 `content`），避免打爆合宙芯片 1KB UART TX FIFO；
2. **射频发射避让静默窗**：发射短信时自动激活模组级 6 秒静默窗口（`_sms_tx_busy_until`），跳过后台定时 `get_status` 轮询探测，避免射频功耗拉垮与串口 FIFO 拥塞引发的基带异常重启；
3. **前端防抖与连击熔断**：Web 前端为发送短信按钮与提交表单增加 `isSmsSending` 锁与 3 秒防抖冷却，杜绝重复并发下发。

### 25.6 固件升级能力门禁与假死消除机制 (FOTA SOTA Hardening)
1. **SemVer 严密数值比对**：上位机引入 `parse_semver` 工具函数提取数字元组 `(major, minor, patch)` 进行能力核验，彻底废除字符串字典序直接比对，杜绝未来 `v1.2.10` 遭误杀与 `"v1.2.4"` 前缀穿透；
2. **能力门禁与 Fast-Fail 拦截**：`/api/control/upgrade_info` 依据 `parse_semver >= 1.2.6` 判定 `sota_supported`。针对未具备 SOTA 桩的旧版本固件（如 v1.2.4）或跨芯片平台（EC618），`/api/control/upgrade_script` 在 0.01s 内 Fast-Fail 返回 HTTP 400 与清晰指引，杜绝 8 秒通信无响应死等；

## 27. 上位机 MCP 零信任授权门禁与多卡集群调用治理架构规范 (AIR-36 Zero-Trust MCP Governance & Multi-Slot Coordination)

针对外部 AI Agent（Claude Desktop / Cursor / Pi）接入蜂窝通信网关时存在的资费偷跑隐患、后台孤儿进程争夺物理端口、多卡集群盲目路由及验证码守候盲等超时缺陷，确立以下系统级治理规范：

### 27.1 方案 D 架构：IPC 单端口免检信任环与双重物理门禁
1. **单端口 IPC (`127.0.0.1:17800`) 统一汇聚**：Web 后端与 MCP 客户端共用同一底层通信中枢端口，彻底消除多端口监听带来的资源冗余与防火墙冲突；
2. **内部免检信任环 (Zero-False-Positive Whitelist)**：
   - 上位机 Hub 启动时在本地数据目录生成随机 Session Token（`.hub_session_token`），并在内存维护信任令牌哈希；
   - Web 后端（`gateway_web.py`）读取该令牌，并在下发指令时声明 `source: "web"` 并携带令牌；
   - Hub 收到内部免检请求时 100% 直通放行，管理控制台的发信、拨号、重启等运维操作绝对不受 MCP 开关影响（零误杀）；
3. **外部未认证请求双重物理门禁**：
   - 外部客户端（`gateway_driver.py`）显式标记 `source: "mcp"`；
   - 出厂默认配置 `"mcp": { "enabled": false, "port": 17800 }`，默认处于物理隔离安全态；
   - 当开关关闭时，放行只读探针（`list_dongles`、`status`、`ping_device`），并在 `list_dongles` 中注入 `"mcp_action_allowed": false`；
   - 物理敏感指令黑名单（`send_sms`、`call_dial`、`call_hangup`、`get_history`、`set_rndis`、`set_cellular_data`、`reboot`、`clear_history`）实施 100% 物理拦截（HTTP 403 / JSON-RPC 拒绝），并阻断 `sms_received` 实时短信事件广播，防范隐私泄露。

### 27.2 客户端孤儿进程根除与时序治理
1. **彻底废除 `_auto_spawn_hub()`**：MCP 客户端绝不允许私自通过 `subprocess.Popen` 在后台盲目启动 Hub 进程，从根源杜绝 Windows 僵尸孤儿进程与端口争用；
2. **连接不可达 Fast-Fail**：当 Hub 未启动时，客户端立即抛出大白话错误 `无法连接通信网关：上位机网关中枢未运行`，杜绝死锁与无响应；
3. **验证码守候 Fast-Fail 门禁**：在 `driver.wait_for_otp()` 与 MCP Tool `cellular_wait_for_otp` 入口处增设门禁检查，MCP 处于未授权禁用状态时毫秒级直接报错拒绝，彻底根治在条件变量上盲等超时 20 秒的重大时序缺陷。

### 27.3 多卡集群元数据透传、同网亲和出站调度与 VoLTE 优选兜底
1. **卡槽全景元数据矩阵**：`list_dongles` 输出规范化结构，包含各卡槽的型号、芯片架构(BSP)、物理端口、在线状态、ICCID、CSQ 信号及动态能力矩阵（VoLTE 语音/FOTA 升级）；
2. **出站分流策略矩阵**：支持四大路由策略（`operator_affinity` 同网优先、`round_robin` 轮询、`signal_best` 强信优先、指定 `slot` 直发）；
3. **VoLTE 语音呼叫硬件门禁**：发起通话时自动优选具备 VoLTE 硬件协议栈且在线的卡槽（如 Air780EPV），对明确不支持语音的模组（如 Air780E）实施 Fast-Fail 拦截；
4. **全集群 OTP 并行监听与卡槽溯源**：验证码守候机制在 1~N 模组集群下并行监听全部健康卡槽，短信到站瞬间毫秒级唤醒，并在返回数据中明确携带 `from_slot` 与 `receiver_phone` 溯源字段。

### 27.4 Web 控制台系统设置抽屉 Apple 风毛玻璃虚化与 AI 提示词模块
1. **极简大白话去工程化**：废除生硬黑话，直接以“启用 MCP 通信服务 · 中枢端口 17800”呈现，状态徽章清晰标明 `🟢 运行中 · 17800` 或 `⚪ 未启用 (安全隔离)`；
2. **AI 专属接入提示词**：抽屉内置面向外部 AI（Claude/Cursor/Pi）的标准提示词框与 `[📋 复制提示词]` 按钮，支持点击框体即时复制，并附带 Toast 反馈；
3. **Apple-style 12px 高斯毛玻璃遮罩**：打开抽屉时左侧工作区呈现深邃磨砂柔焦虚化，点击左侧大面积毛玻璃背景或按下 `ESC` 键，抽屉平滑自然滑回收起。

### 29.1 架构初衷与零猜词设计
针对多模组集群（Air780E / Air780EPV / Air780EPM / Air700E 等）混插场景，废除此前散落在各处的模糊匹配或针对特定字符打补丁的设计，确立单源字典定义与日常展示原样透传原则：

- **第二梯队（全词精准匹配字典）**：对清洗后的商业型号名执行大写全词匹配；
- **第三梯队（出厂全新 AT 模组伴生口嗅探）**：向串口下发 `ATI` / `AT+CGMR` 等标准指令，通过最长特征前缀树（Longest Prefix Match）自适应识别芯片。

## 31. ITU-T E.118 标准 ICCID 校验与单次探测看门狗 (AIR-56)

### 31.1 未插卡脏数据与“假物联卡”根除
未插卡模组在伴生口持续输出底层 Trace 调试日志，日志中包含 `[000000000000000000]` 时间戳或进程 PID，此前被正则盲读误提取为 19 位卡号并主观脑补为“物联卡 (无本机号)”。

### 31.2 国际标准硬门禁与过滤管线
- **ITU-T E.118 格式强校验**：电信 SIM 卡号必须满足：
  1. 必须以电信国际标识 `89` 开头；
  2. 纯数字长度严格限制在 19 或 20 位（允许末位携带 1 位十六进制校验码 `F`）；
- **调试行前缀阻断**：严禁在带有 `[TRACE]`、`[DEBUG]`、`HEX:`、`AT+` 等回显日志行中贪婪正则提取；
- **真实未插卡判定**：当板端上报未插卡、或 ICCID 无法通过 ITU-T E.118 门禁时，前端统一渲染纯净的黄色警示标 `未插卡`，严禁脑补“物联卡”字样；
- **单次探测看门狗**：`DongleSession` 针对每张卡槽设立单次开机探测限频，探测完成后锁定，仅在发生物理热拔插断开时重置自愈，彻底杜绝日志盲读死循环。

## 35. 原生单实例桌面客户端与托盘生命周期架构 (AIR-69)

### 35.1 架构演进与技术定论
上位机彻底推翻原先“后台常驻 Web 服务 + 外部命令行调用 Edge 浏览器 `--app` 伪装窗口”的脆弱架构，确立**“原生单实例 Microsoft Edge WebView2 宿主容器（通过 pywebview）+ 独立线程系统托盘（pystray）”**的工业级桌面架构：

4. **低功耗休眠联动 (AIR-64)**：窗口缩入托盘时，宿主层调用 `CoreWebView2.TrySuspendAsync()` 挂起渲染管线与 JS 引擎；前端页面监听 W3C 标准 `visibilitychange` 事件自动暂停 4 秒高频轮询，切回前台立即触发自愈心跳与重连，守住静默状态 CPU < 0.1% 基线；

## 40. 业务内核单源收敛与多端分发分治规范 (AIR-70)

### 40.1 双工程镜像架构弊端与单源收敛 (Core + Shells)
历史版本中 `tools/host_gateway` 与 `tools/cluster_gateway` 双目录并行维护，导致业务逻辑与前端界面每次修改都需要手动双向镜像同步，极易滋生不一致性缺陷。AIR-70 彻底消除双工程镜像负担，确立 **业务内核单源收敛（Core） + 多端分发分治（Platforms/Shells）** 现代软件架构：
1. **单一事实源内核 (`core/`)**：
   - 跨平台守护与中枢：`core/gateway_hub.py`
   - 跨平台 Web 控制台与 REST API：`core/gateway_web.py`
   - 分舱存储与权威时序：`core/storage_manager.py`
   - 物理卡槽动态路由与集群分发：`core/cluster_router.py`
   - 多卡健康看门狗：`core/cluster_health.py`
   - 跨平台固件升级与烧录管线：`core/firmware_flasher.py`、`core/luadb_packer.py`
   - 唯一跨端响应式控制台：`core/web/index.html`、`core/web/favicon.ico`
   - 跨平台运行时与确定性寻址适配：`core/runtime.py`（提供数据、日志、缓存、Web 根目录自适应探测及 `directory(kind)` 向下兼容垫片）
2. **多端分发外壳 (`platforms/`) 物理隔离**：
   - Windows 桌面独立端 (`platforms/windows/`)：包含原生托盘与生命周期外壳 `gateway_app.py`、打包流水线 `build_exe.py`、图标与规格定义。
   - 飞牛私有云 NAS 套件 (`platforms/feiniu_fnos/`)：包含官方原生套件元数据 `manifest`、权限配置 `config/privilege`、资源配置 `config/resource`、入口 `cmd/main`、生命周期回调 `cmd/*_callback`、向导 `wizard/`、离线 vendored `pyserial`、构建脚本 `build_fpk.py`。
   - 硅基涌现应用平台 (`platforms/silicon_emergence/`)：受管入口为 `gateway_managed.py`，权限/路径适配为 `gateway_runtime.py`，设备通道为 `gateway_device_channel.py`；构建器消费core，不复制Hub/Web/存储业务。原 `gateway_bridge_silicon.py` 保留其原用途，不是本次插件的启动入口。
3. **向下兼容过渡与安全收敛**：
   - 彻底安全移除历史冗余 `tools/cluster_gateway`（移入系统回收站）。
   - 保留 `tools/host_gateway` 作为纯向下兼容垫片，软链接或镜像代理至 `core/`，杜绝破坏历史脚本与自动化流水线。

### 40.2 飞牛私有云 (fnOS) 官方原生套件规范
针对飞牛 EVO4 NAS 等家庭私有云 7×24 小时开箱即用需求，严格遵循飞牛官方《应用中心套件开发规范》：
1. **零外部网络开箱即用 (Vendored pyserial)**：
   - fnOS 套件安装与运行严禁在线执行 `pip install`。
   - 将纯 Python 实现的 `pyserial` 源码完整内嵌于 `platforms/feiniu_fnos/app/vendor/serial`，通过 `cmd/main` 运行时动态前置 `PYTHONPATH` 实现绝对离线开箱即用。
2. **路由与资费安全保障 (NM_UNMANAGED="1")**：
   - 4G 模组插入 NAS 时，严禁 Linux NetworkManager 自动将其识别为默认宽带路由，防止多卡保号卡流量偷跑或冲撞家庭千兆有线宽带。
   - 套件安装回调 (`cmd/install_callback`) 自动向宿主机 `/etc/udev/rules.d/99-cellhive-dongle.rules` 写入 `ENV{NM_UNMANAGED}="1"` 与 `ENV{ID_MM_DEVICE_IGNORE}="1"` 规则，并重载 udev。
3. **守护进程级联管理与原子文件锁 (PGID & flock)**：
   - 套件后台守护进程由独立作业控制组（PGID）管理，严禁遗留孤儿进程霸占串口或 Web 端口。
   - 启动脚本 `cmd/main` 使用 `flock` 原子排他锁保障服务单实例运行；终止进程组时严格设立 `PGID > 1` 安全防线，避免意外波及 PID 1 操作系统根进程。
4. **数据资产安全保留选项**：
   - 卸载向导 (`wizard/uninstall`) 默认开启“保留历史短信记录与配置数据”复选框；
   - 仅在用户显式取消勾选时，卸载回调才清理 `$TRIM_PKGVAR` 数据目录，保障用户数字资产绝对安全。


### 40.3 当前受管接入与共同源码（AIR-46，2026-10-08）

公共业务仍只维护core；Windows壳默认Serial和完整维护功能，硅基壳注入受管transport、显式data/config/cache/log目录及能力/生命周期。core不反向导入平台壳。`initialize`只进入prepared，HTTP在所有handler之前统一鉴权和能力判断；`activate`显式初始化归档后启动Hub/Web。关闭未确认保留会话待重试，未知写入不自动重放；数据按卡分舱，未知归属不借首卡，旧history只读，损坏墓碑拒绝覆盖。

`core/runtime.py`提供单一BUSINESS_VERSION及路径助手。Windows入口把data/config设到同一个LOCALAPPDATA/CellHive/data目录；本轮未搬移或合并旧桌面目录，也没有切换运行EXE。两处已有数据的接续验证与Windows完整依赖/维护资产来源仍是后续Windows交付条件。受管模式只用宿主显式目录，不回退到源码、TRIM或用户桌面目录。

插件与Windows构建器消费相同8项core集合，来源记录区分实际字节SHA、现有Git过滤后的保存关系以及独立依赖/资产。插件构建已形成1.4.0候选；它不包含Windows维护资源。两端完整制品、UAT与真板结果分别判断，不由源码接受推出。当前构建和更新入口见[操作说明v2](../changes/0046-适配-上位机受管插件更新/managed-plugin-update-runbook-v2.md)，实际接受范围见该Change的tasks及复审记录。
